# Internationalization (i18n)

Multi-locale support for **both** the web UI and the REST API. Supported locales come from
`config('app.available_locales')` (default: `en`, `id`). Adding a locale = one config entry +
the two `lang/<locale>/*.php` files + a re-seed (no code change).

## How locale is resolved

Two separate channels — web (stateful/session) and API (stateless/token) — because the API
group is stateless (Sanctum Bearer) and has no session.

### Web (browser)
- `LocaleController@update` (POST `/locale`) validates the locale against `available_locales`,
  stores it in the **session** (`locale`), and redirects back.
- `SetLocale` middleware (registered in the `web` group in `bootstrap/app.php`, **after**
  `StartSession`) reads `Session::get('locale')` and calls `App::setLocale()`.
  - **Ordering matters**: it must run *after* the session starts, or the session read returns
    null and every request falls back to `en`. (This was the original "language switch does
    nothing" bug.)

### API (JSON)
- `SetApiLocale` middleware (registered in the `api` group in `bootstrap/app.php`) resolves the
  locale **without a session**, from (in priority):
  1. `X-Locale` request header
  2. `Accept-Language` header (first matching supported locale)
  3. `en` fallback
- Controllers return user-facing strings via `__('messages.*')` so the resolved locale is applied.

## Translation sources (file → DB override)

Strings live in two PHP files per locale, split by **usage context** (never mix
the two in one call — `ui()` calls a key from `ui.php`, `__('messages.*')`
calls one from `messages.php`):

| File | Scope | Used by |
|------|-------|---------|
| `lang/{locale}/messages.php` | Domain / API / flash messages + content copy | web + API (`__('messages.*')`) |
| `lang/{locale}/ui.php` | Page-level copy: labels, headings, buttons, nav, modals, table headers | web only via `ui()` helper |

**Group discipline (root-cause convention — keeps files DRY, no key duplication
across groups):**
- Put it in `ui.php` when the string is **interface chrome** the user sees
  regardless of domain: button text (`save`, `cancel`), nav labels (`dashboard`,
  `users`, `settings`), headings, table column headers, modal titles, breadcrumbs.
- Put it in `messages.php` only when the string is **domain/API/flash content**:
  validation/error messages, API JSON responses, account-status copy, email text,
  per-feature help text, confirmation dialogs, flash feedback.
- **A key must live in exactly one group.** If unsure, `ui.php` wins (chrome).
- **No new groups.** Do not create a `plans.php`, `billing.php`, etc. namespace —
  every UI label belongs in `ui.php`, every feedback message in `messages.php`.
  See §7 (Rules for Hermes) for the decision tree.
- Never hardcode English in Blade. No `?? 'fallback'` English defaults in views.

- `app/Helpers/i18n.php` provides `ui($key, $replace = [])` — a thin wrapper over
  `__('ui.'.$key, $replace)`. Views call `{{ ui('sign_in') }}` instead of hardcoding English.
- **DB override**: `spatie/laravel-translation-loader` loads `language_lines` (seeded by
  `LanguageLineSeeder`, which syncs **both** `messages` and `ui` groups from the files). A row in
  `language_lines` overrides the file at runtime — edit translations in the DB (Settings →
  Translations UI) without touching code. The file remains the fallback/source of truth.

## Adding / editing a string

- **New English copy** → add the key to `lang/en/ui.php` (or `messages.php` for API/domain).
  Mirror it in `lang/id/ui.php`. Re-seed with `php artisan db:seed --class=LanguageLineSeeder`
  to push into `language_lines`.
- **Runtime override without redeploy** → edit the row in the Translations admin UI.
- **New locale** → add to `available_locales` in `config/app.php`, create
  `lang/<locale>/{messages,ui}.php`, re-seed.

## Tests

|`tests/Feature/LocaleTest.php` covers:
|- session persistence of the chosen web locale
|- `SetLocale` applies session locale (incl. DB override from `language_lines`)
|- end-to-end web render switches to Indonesian (`/dashboard` shows "Dasbor")
|- `SetApiLocale` resolves `X-Locale` and falls back to `en` for unsupported values
|- **e2e API**: login → logout with `X-Locale: id` returns `{"message":"Berhasil keluar."}`;
  no header returns the English `"Logged out."`

## Automated validation

- `php scripts/i18n_audit.php` — standalone file-level parity + placeholder check (no Laravel context).
- `tests/Feature/TranslationTest.php::keeps en and id locales structurally consistent`
  — integrated Pest test: asserts key parity + placeholder parity across `en`/`id` for `ui` and `messages`.
- `LanguageLineSeeder` (idempotent) syncs file keys into `language_lines`
  and **deletes** stale DB rows whose key no longer exists in the lang files.

## Namespace consolidation history

- **`plans.php`** (en + id) was removed in `b165bf6` (i18n standardization).
  Its two keys were app-specific validation messages (`feature_limit_exceeded`,
  `permission_feature_mismatch`), not UI labels — migrated to `messages.*`.
  See §7 (Rules for Hermes) for the decision tree and usage rules.

## Rules for Hermes

- Before creating a new translation key: search existing `lang/{en,id}/*.php`.
- Reuse an existing key whenever semantically appropriate.
- `ui` = static interface terminology; `messages` = contextual feedback.
- `validation` = framework validation messages only.
- Do NOT create a new namespace without architectural justification (ADR).
- Keep all locales structurally consistent — run the parity test.
- Preserve placeholders across all locales.
- Do not hardcode user-facing text in Blade/controllers/API responses.
- Do not put business logic, authorization logic, or secrets into translations.
